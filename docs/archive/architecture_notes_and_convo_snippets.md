* The domain/topic priors that will guide article granularity
* Canonical formatting conventions for all downstream phases

Input: one raw source document Output: one cards/{doc_id}.card.md persisted to disk/DB Parallelism: embarrassingly parallel, zero dependencies between docs

* A concise synthesis (2–4 paragraphs) of the document's core contribution
* A list of 5–10 candidate concept headings — what wiki articles would this document inform?
* Key claims or facts, attributable to this source
* YAML frontmatter: tags, source type, date, salience signal

The candidate concept headings are intentionally loose and redundant — you're not worried about "Machine Learning" vs "ML" vs "machine learning algorithms" here. That gets resolved in Phase 2.

Phase 2: Concept Registry Construction (global, cheap, runs after every batch)
Input: all *.card.md files across the entire vault Output: registry/concepts.json — the canonical article namespace Parallelism: the embedding step is parallel; the merge step is a single fast pass
This is the one phase that must see the full corpus, but it can afford to because cards are concise. The process:
1. Embed all candidate concept headings from all cards (fast, parallelizable, cheap)
2. Cluster semantically similar headings using hierarchical clustering with a fixed threshold — this is deterministic given embeddings and produces the canonical concept list
3. For each cluster, LLM picks a canonical article title + 1-sentence description (or you use the centroid label, but LLM quality is better)
4. Map each card to its top-N most relevant concepts (many-to-many)
The result is a stable concept namespace that grows and refines as more documents arrive. Adding 100 new docs mostly adds new concept clusters at the margins or slightly expands existing ones — it doesn't reshuffle everything. The Wikipedia analogy is apt: new articles get added without invalidating existing ones.
This is also where you control abstraction quality. The clustering threshold is your single most important tuning knob. Too fine → thousands of hyper-niche stubs. Too coarse → monolithic articles. You want clusters that correspond to real intellectual units — and you can hint at this by including domain priors in Phase 0's schema and using them to inform the clustering merge step. Over time, a "lint" operation (Phase 5) identifies articles that have grown too broad and flags them for splitting.

This is where worldview vs. research mode diverges:
* Research mode: "Write an encyclopedic article about {concept} covering what the following source documents say, with inline citations."
* Worldview mode: "Write an article about {concept} as understood through the lens of the following sources, as if writing from within the perspective they collectively embody."
Both modes produce articles with explicit [[wikilinks]] to other concept names from the registry (the LLM knows the concept namespace from the registry). These links are inserted naturally during drafting — not post-hoc — because the LLM can see the full concept list.
The key insight here: each article is written using cards, not raw documents. The LLM never has to fit 10,000 documents into context. It only has to fit the subset of concise cards relevant to that concept. This is what makes the whole thing scale.

* Scan each article for mentions of canonical concept names from the registry (fuzzy match, not exact)
* Insert [[wikilinks]] where they're missing
* Build a backlink index so each article knows what links to it
* Flag any mentions of concepts that appear in the registry but don't have their own article yet ("missing article" signals)
This phase is what makes the wiki feel like a graph rather than a collection of stubs. And because it runs after all articles from the current pipeline run are compiled, articles from old batches and new batches link to each other naturally.

Phase 6: Lint (periodic, async)
Input: entire wiki state Output: a lint-report.md with flagged issues
Run periodically or on demand, not on every ingestion cycle. Checks for:
* Orphan articles (no inbound links)
* Articles that have grown too long → candidates for splitting (which means adding a new concept to the registry and re-running Phase 3 for the affected concepts)
* Contradictions between articles
* Concepts mentioned in articles that lack their own page
* Cards that reference concepts not in the registry (new candidate concepts that didn't cluster above threshold)
Importantly, lint results feed back into the registry and trigger targeted re-runs of Phases 3-4 for affected articles only. This is the mechanism by which the wiki self-improves over time.

Incremental Update Flow
When you add a small number of new docs (the "trickle" case):
1. Phase 1 — run only on new docs → new cards
2. Phase 2 — re-run globally over all cards (cheap, since cards are concise) → possibly new concepts or expanded mappings
3. Phase 3 — run only on concepts that changed (new concept entries or concepts with newly added card mappings). Unchanged concepts are untouched.
4. Phase 4 — re-run cross-linking on all articles that changed in Phase 3, plus any existing articles that now reference the new concepts
5. Phase 5 — rebuild index and sync

“””Why headings alone for clustering
The goal of Phase 2 isn't to cluster documents by similarity — that's RAG, which is what you're trying to transcend. The goal is to build a concept namespace: a set of distinct article-worthy ideas. The LLM already did the semantic distillation work in Phase 1 by extracting concept headings. Those headings are pre-semanticized labels — they're the LLM saying "this document is evidence for a concept called X." Embedding them gives you clean signal about conceptual identity.
If you embed full card content — claims, frontmatter, anchor text all bundled together — you get document similarity clustering instead of concept clustering. Two cards about very different topics might share similar boilerplate claims or framing ("this has implications for AI safety...") and cluster spuriously. The heading strips out everything except the concept label itself, which is exactly what you want when constructing a namespace.
There's also a stability argument: headings are short, canonical-ish phrases, so their embeddings sit close to what the model natively "thinks" those concept regions are. Full-card embeddings shift based on phrasing, document length, claim specificity — lots of noise for a task that just needs "are these two concept labels the same idea?"
The partial exception: card synthesis as disambiguation context
There's one case where additional signal genuinely helps in Phase 2: homonyms. "Attention" means something different in cognitive neuroscience than in transformers. "Networks" differs between neuroscience, computer networks, and social network theory. In those cases, embedding the heading alone can force spurious merges.
The right answer isn't to embed the full card — it's to embed the heading with the one-sentence synthesis appended as context, weighted toward the heading. This gives the model enough grounding to place "attention (cognitive)" and "attention (transformer)" correctly without contaminating the embedding with claim-level noise.
What each other field actually does downstream
Key claims/facts are the primary input to Phase 3. When the LLM writes an article about concept X, it's synthesizing across the key claims from every card mapped to X. These are the substance. They're also what generates inline citations in the final articles — "Source Y argues that Z" comes directly from the claims extracted in Phase 1.
YAML frontmatter (tags, date, source type, salience) serves three purposes. First, it mirrors to your Postgres tag table for the agent's SQL query tool — so the agent can answer "what do my sources from 2019-2021 say about X" with a structured query rather than RAG. Second, it affects prioritization: when new sources arrive and you need to decide which articles to recompile in Phase 3, salience and recency signals tell you what to touch first. Third, in worldview mode specifically, source type metadata matters for how claims get weighted — a primary source gets treated differently than a commentary or synthesis.

Headings cluster cleanly because they're already abstracted concept labels. Claims are content. Frontmatter is the structured query layer and the priority/provenance signal. Convergent compilation means that the same corpus, regardless of ingestion order or batch size, produces approximately the same wiki. Approximation determinism means that recompiling from the same inputs produces outputs that are semantically equivalent even if not lexically identical, because LLM calls are stochastic. Contradiction flagging, cross-link gap detection, and split/merge suggestions are all mechanisms for reducing the distance between the actual wiki and that fixed point.
