# M4 — Compile pipeline, workers, and durable workflows

**Parent plan:** `docs/ts-migration.md`. **House rules:** `docs/ts-migration-m1.md` (binding). **Prior art:** `SPIKE_REPORT.md` Round 2 (the proven single-node `ClusterWorkflowEngine` + `SingleRunner` durability pattern; the spike `workflow-*.ts` files are reference, then deleted here).

**Objective:** the TS backend runs the complete seven-phase compile pipeline and all worker tasks on Effect durable workflows, byte-faithful to Python where deterministic and statistically faithful where LLM-driven — completing the backend surface so M5 is only staging parity and cutover.

**Non-goal (hard rule):** NO algorithm changes. The canonicalize/registry-stability redesign (`compile-v2`, the confluence architecture) happens AFTER cutover as its own workstream — it must not tangle with this port. Where the current algorithm is known-imperfect (over-merge, registry variance), port it faithfully; the characterization harness pins today's behavior, not ideal behavior.

MarkItDown conversion — the M3.2 decision-13 binary-conversion deferral lands here; `compile_task` orchestration, retry/idempotency via Absurd today), compile-intents reconciler, pipeline-runs lifecycle, cancellation/retry semantics.

## Task breakdown (sequenced, review gate between each; Codex on gpt-5.6-sol — high reasoning for kernel tasks, medium for mechanical)

**M4.1 — Golden-compile characterization harness** (the M2 second half; BEFORE any pipeline port). Fixture corpus checked in; runs the PYTHON pipeline against a scratch stack to record goldens: exact artifacts (hashes, cache keys, partition assignments, DB rows, file trees) and statistical envelopes for LLM-dependent outputs (registry size bounds, membership distributions — seeded from the probe-findings methodology). Harness then replays against either backend. LLM calls for goldens: stub-recorded (cassette) so the harness is hermetic and free; one env-flagged live mode.
**M4.2 — Durable workflow foundation + workers.** Effect workflow/cluster engine layer in the server (spike pattern productionized, house rules); port `staged_file_ingest` (incl. full binary conversion — MarkItDown-equivalent; revisit the M3.2 conversion stack for pdf/docx or justify additions) and the compile-intents reconciler + pipeline-runs lifecycle. Absurd coexistence note: TS workflows REPLACE Absurd post-cutover; during M4, TS tasks enqueue/execute on the Effect engine while Python/Absurd remains prod — the queue-compat constraint from M3.2 dissolves at cutover (record the transition plan).
**M4.3 — Pipeline phases: deterministic spine.** ingest, publish, verify, derive + the compile_task orchestration workflow with progress-step emissions and the job SSE stream + compile/job/lint/cost HTTP routes. Characterization: exact-match against M4.1 goldens.
**M4.4 — Pipeline phases: LLM core.** extract, abstract (partition/premerge/canonicalize/synthesize/validate), render — faithful ports of prompts (drift guards), structured-output schemas, cache-key construction (exact), truncation/failure handling per the hardened Python behavior. Characterization: exact on cache keys/deterministic substeps, statistical on LLM outputs via M4.1 envelopes with recorded-cassette determinism in CI.
**M4.5 — Closeout**: full-pipeline golden run green both backends; browser smoke driving a real compile from ingest to published wiki on scratch data (live LLM, small corpus); punch list; docs.

## Rules (delta)

- Zero changes to `src/great_minds/`, `web/src/`, DDL (alembic still owns schema; the Effect cluster tables are created by the engine's own migrations — document where they land and confirm no collision with alembic's tables).
- The progress-steps taxonomy and job SSE protocol are contract (the pipeline UI is the oracle).
- Every LLM phase behind stub-recordable seams; no live LLM in CI.
- Faithful-port rule: where Python behavior is known-buggy, the M1 process rule applies (flag for decision, don't silently fix or replicate) — EXCEPT algorithmic quality issues (over-merge etc.), which are explicitly ported as-is per the non-goal.

## M4.2 decisions

1. **Engine storage and bootstrap.** `packages/server/src/workflow-engine.ts` runs `ClusterWorkflowEngine` with `SingleRunner` against the same `DATABASE_URL`/`PgClient` as the application. Effect owns exactly three unqualified `public` tables: `cluster_migrations` (the engine migration ledger), `cluster_messages` (durable workflow/entity requests, activity requests, delivery state, and deduplication keys), and `cluster_replies` (durable activity/workflow exits and reply chunks). The engine's `SqlMessageStorage` layer runs its idempotent `Migrator` during layer construction, before handlers accept work; scratch tests deliberately drop all three tables and prove that the first runner recreates them automatically. Alembic neither declares nor drops these tables. An Alembic-head scratch database plus engine bootstrap was exercised by `workflow-kill-resume`; there are no name, type, index, or migration-ledger collisions. The two migration systems coexist because Effect uses only the `cluster_*` namespace and its own ledger while Alembic continues to own every product table.
2. **Runner registration is ephemeral; the journal is durable.** Production uses `SingleRunner.layer({ runnerStorage: "memory" })`. This removes the SQL runner/shard lease that remained stale for roughly 35 seconds after a SIGKILL in the spike. It does not make workflow state in-memory: `SingleRunner` still installs SQL `MessageStorage`, so `cluster_messages`/`cluster_replies` survive process death and are replayed immediately by the replacement process. This is the intended single-process deployment shape; multi-runner coordination would require revisiting runner storage and health/communications together.
3. **Activity side effects are idempotent, and the terminal branch is journaled.** The pinned beta's `ClusterSchema.WithTransaction` path was exercised and rejected: an activity using the same `@effect/sql-pg` client hung after its application insert while pg warned about a concurrent query. Production therefore uses ordinary durable activities and makes each external effect replay-safe: staged R2 destinations are content-addressed and overwritten deterministically, document writes upsert on `(vault_id,file_path)`, compile intents coalesce through the partial unique index, task rows use stable workflow ids, and staging deletes are idempotent/best-effort. Staged ingest is two activities: `staged-file-ingest-persist` fetches/converts/flushes and journals `{ingested,skipped,failed,cleanupHashes}`; `staged-file-ingest-finalize` chooses compile/all-failed/all-deduped from that journaled result, then creates the intent, cleans staging, and emits terminal progress. Once the persist result is journaled, the branch is never recomputed from rows written by a prior attempt. Residual window, matching Python's Absurd-retry hole: a crash between the last batch flush and persist's own journal commit re-executes persist, whose re-run dedupes the rows attempt one already flushed and journals them as skipped — documents persist but the run finalizes all-deduped with no intent. Closing it needs per-batch journaling or attempt-scoped dedupe; deferred as a faithful-port hole, not silently. `workflow-kill-resume` proves completed activities do not replay, and `resume-after-persist preserves the journaled ingest decision and creates the intent` SIGKILLs between these production activity names, then proves the document is not re-read and the intent survives.
4. **Conversion surface and known gaps.** `officeparser@5.2.2` handles PDF, DOCX, PPTX, XLSX, ODT, ODP, and ODS from in-memory buffers; Markdown/text plus CSV, JSON, and XML decode as strict UTF-8. HTML uses `Readability` + Turndown. This is intentionally narrower than Python's rule of sending every non-text extension through MarkItDown: TS still drops EPUB and ZIP archives, legacy XLS, Outlook MSG, notebooks/IPYNB, images, audio, RSS, and other formats accepted through MarkItDown's generic/plugin detection. HTML is also not byte/render faithful: Readability article selection and Turndown formatting can differ from MarkItDown, so the rendered markdown and its `file_hash` may diverge even for the same HTML upload. Those are explicit fidelity gaps for a later dependency decision, not claims of full MarkItDown equivalence.
5. **Staged ingest isolation, retry, and progress.** Fetch/conversion concurrency remains four and DB flush size remains fifty. Python drains `asyncio.as_completed`; TS preserves input order after concurrent fan-out, and no contract artifact depends on write order. R2 staged reads/deletes now expose typed `StorageFileMissing`/`StagedStorageError` failures; missing staging objects are expected domain failures. Each fetch/conversion slot is captured with `Exit`, so typed failures and adapter defects both become that file's failure without aborting siblings. Cleanup is also captured per key; failures are counted and logged and never fail the activity. The final `index_documents` progress snapshot is emitted unconditionally, including zero-row/all-skipped runs, and file logs retain the actual failure/defect type. Each of the two activities uses `Activity.retry` with one additional attempt (two attempts total), matching Python's `max_attempts=2` at the durable engine seam. Mixed success completes and queues one intent; all-failed fails; all-deduped emits synthetic `publish/completed`; cleanup remains after the intent/document commit.
6. **Terminal stability and journal-backed zombie recovery.** Python permits late progress to resurrect `failed`/`cancelled` runs and lets generic failure clobber cancellation. TS progress updates, including the compile workflow, route through `PipelineRunsService` and update only `pending|running`; terminal rows cannot be overwritten. Recovery evaluates only stale `pending|running` rows. A row with `active_task_id` is failed only when no matching `Workflow/StagedFileIngest` or `Workflow/CompileTask` request exists in `cluster_messages`; this closes the task-row/active-id/execute crash window without falsely failing a live or resumable workflow. A row with no active task is exempt while attached to an unsatisfied compile intent, because pending or dispatched-behind-an-active-vault work is queued, not zombie. Intent satisfaction additionally requires `dispatched_at`, `dispatched_task_id`, a terminal guarded run, and the matching compile-workflow journal request, so a pre-dispatch zombie failure cannot silently satisfy its intent.
7. **Compile seam, loop composition, and outbox lifecycle.** The HTTP `AppLayerLive` contains the workflow engine and handlers needed by routes but never the reconciliation loop. Only `packages/server/src/main.ts` merges `CompileIntentReconcilerLoopLive`; integration suites opt in explicitly when needed, and the parity harness launches its HTTP-only runner and asserts that TS created no compile-workflow journal request and dispatched no intent. A pass marks eligible dispatched intents satisfied, opens a short transaction that locks pending intents oldest-first with `FOR UPDATE SKIP LOCKED`, skips a vault with an active compile, and creates/attaches a `manual` run for a bare intent. That row lock releases when the transaction returns, before workflow dispatch. The actual cross-pass/process double-dispatch guard is the stable intent id used as the workflow idempotency key and deduplicated by `cluster_messages`; application `tasks` also use that stable id. M4.2's guarded `CompilePlaceholder` was replaced in M4.3a by `CompileTask` while retaining payload `{intentId,vaultId,pipelineRunId}`.
8. **Absurd transition.** Throughout M4, TS enqueue/execution writes only Effect's `cluster_*` journal plus the application `tasks`/`pipeline_runs`/`compile_intents` rows; it never inserts into or executes from `absurd.*`. Python/Absurd remains the production deployment until M5. At cutover, stop new Python writes, drain all in-flight Absurd staged-ingest and compile tasks to a terminal state (failed/cancelled tasks are resolved or explicitly abandoned), run one final Python reconciler pass so their intents receive `satisfied_at`, then start the TS engine/reconciler. Do not translate Absurd step ledgers or copy in-flight tasks into Effect. Any intentionally abandoned intent is reset/re-emitted as a new Effect workflow after cutover. Once drained, Absurd queue compatibility from M3.2 is removed and its tables become inert legacy data pending a later explicit retirement migration.
9. **M4.3a compile identity and journal spine.** Decision 7's handler-only swap is implemented as `Workflow/CompileTask`, retaining payload `{intentId,vaultId,pipelineRunId}` and intent-id idempotency. The phase activities are `compile-phase-ingest`, `compile-phase-extract`, `compile-phase-abstract`, `compile-phase-derive`, `compile-phase-render`, `compile-phase-verify`, and `compile-phase-publish`, in that order. Abstract's journaled return is the validated-topic value threaded into derive/render; the zero-topic branch is therefore replay-stable. The parity guard, reconciler satisfaction query, and zombie-recovery entity list changed with the workflow tag in the same edit. Extract and abstract fail with schema-encoded `CompilePhaseNotPorted`; render first performs its deterministic cache classification/materialization and raises the same typed error only if an LLM render is actually required. M4.4 replaces these service methods without changing the workflow or activity names. Granularity note: render runs as ONE activity, whereas Python's Absurd render used per-topic sub-steps (render.py:509-516) — a mid-render crash re-executes the whole phase, with per-topic render-cache hits making the re-run cheap; revisit only if M4.4 observes materially long fresh-render phases.
10. **Cancellation delivery on the in-process runner.** Cancellation first performs `PipelineRunsService.cancel`'s guarded `pending|running` update (`status=cancelled`, `phase_status=failed`) and then calls the active engine's `interruptUnsafe` while the same provided `SingleRunner` layer is alive. The routed `Workflow.interrupt` client path was rejected for this topology: without a separate healthy remote runner it can wait in sharding instead of interrupting the local activity. `interruptUnsafe` still writes the durable interrupt signal before local delivery. Phase failure/progress writes remain guarded, so cooperative teardown cannot clobber `cancelled`.
11. **Deterministic shells around M4.4 seams.** M4.3a owns every exact operation that can run without a chat model, even where it surrounds an unported LLM call: all six cache-key recipes are exported and pinned; render cache hits, missing-file materialization, invalid-cache fallthrough, article persistence, and wiki re-indexing are live; validate's mechanical archive/supersession file+row transition is exposed for the M4.4 cleanup decision to call. A cache miss never fabricates output: it reaches a typed M4.4 seam. The Python compile log remains local-only, but publish adds a journaled `compile-publish-timestamp` before the publish activity and de-duplicates that exact append block. This preserves Python's timestamped bytes while closing the replay window that would otherwise append the same compile twice after a crash. Recorded oracle divergence: Python's wiki re-index inside render emits progress under phase="ingest" for both scopes (search/service.py:278-288,379-388), a UI wart; TS emits re-index progress only for the raw scope. The golden taxonomy aggregation tolerates this, and the M4.4 goldens seam licenses it explicitly.
12. **Fresh-mint compile submission returns 202 (Python live bug #6).** Python's `request_compile` inserts the intent with `pipeline_run_id=job_id` before any run exists (compile_intents/service.py:29); the non-deferrable FK raises IntegrityError, so `POST /compile` with a client-minted job id on a vault with no pending intent returns 500 in production. TS creates the run first inside the same transaction and returns 202. Deliberate divergence, same family as decision 6; parity covers only the pre-seeded-run path, so the divergence is recorded here rather than as a D-rule. On pure coalesce (pending intent already attached to a run) TS, like Python, does not touch the run row at all — no `updated_at` bump, no spurious SSE snapshot.
13. **Job SSE transport is polling; cosmetic divergences recorded.** TS streams pipeline_runs snapshots by 100ms polling with dedup of identical snapshots, versus Python's LISTEN/NOTIFY re-emits; heartbeats fire every 30s unconditionally versus Python's 30s-of-silence. Event protocol (connected → data snapshots → done, snapshot-on-connect, one-shot terminal close, comment heartbeats, pre-stream authz as HTTP errors) matches the contract and the frontend parser; JSON spacing and timestamp formatting differ only in fields the hook ignores. Cost routes: an empty aggregation window renders `0.000000` (numeric(12,6)) versus Python's `0` — no frontend caller, parity fixtures cover non-empty windows only.
14. **Known parity flake window.** The parity Python backend runs its live reconciler; a pass landing between `mutation-compile-submit` and `mutation-compile-coalesce` would dispatch the seeded intent and mint a fresh one, so Python would return a different run id than the coalescing TS. Millisecond window against a 5s cadence; if it ever fires, rerun — do not mask `id`.
15. **Production-scale partition clustering remains an explicit cutover divergence.** Do not extend the current TypeScript k-means kernel with a partly faithful reassignment or split approximation. The Python environment is locked to scikit-learn 1.8.0 (`uv.lock:1117-1120`). Its `MiniBatchKMeans.partial_fit` invokes `_random_reassign` on every batch (`sklearn/cluster/_kmeans.py:2285-2297`); reassignment is forced for empty centers or every `10 * n_clusters` processed samples (`:2036-2050`), then low-count centers are selected, capped, relocated from uniformly sampled observations, and have their weights reset inside the compiled mini-batch step (`:1648-1679`). Recursive oversize splitting separately calls full `KMeans(n_clusters=2, random_state=42, n_init=1)` (`src/great_minds/core/pipeline/abstract/partition.py:318-339`), whose exact result also depends on sklearn's convergence, empty-cluster relocation, float64 distance path, NumPy RNG, and compiled kernels. Reproducing those semantics in TypeScript is not tractable without embedding the oracle itself; the existing JS kernel is retained unchanged rather than represented as exact. Cutover mitigation: existing partition cache rows are the fixed point and are reused before embeddings are loaded (`partition.py:68-89`), so already-compiled idea sets do not recompute k-means. Divergence is limited to fresh partitions for changed idea sets, a path already nondeterministic across Python runs because UUID ordering changes partition composition (M4.1 finding). The post-cutover `compile-v2` redesign obsoletes this k-means path entirely, so no pre-cutover approximation will be added.
