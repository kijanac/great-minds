# Encrypted vault sync and sharing

> **Status:** exploratory proposal, not a verified decision. This note records a possible architecture for future encrypted sync and sharing.

## Goal

Remote infrastructure should store and coordinate vault data without seeing plaintext source content, article content, search bodies, embeddings, sessions, replies, or compile artifacts.

The remote service can still see some metadata unless further padded/obfuscated:

- account identities
- collaborator graph
- approximate object sizes/counts
- timing of syncs
- device count
- possibly vault IDs or encrypted vault aliases

## Core idea

Treat a vault like an encrypted, append-only, git-like repository:

1. Local runtime stores plaintext in a local DB/object store.
2. Sync layer packages canonical changes into encrypted immutable objects or packs.
3. Each commit references object hashes and parent commits.
4. Commits are signed by device keys.
5. A remote service stores encrypted objects and signed heads.
6. Other devices pull, verify signatures, decrypt, and rebuild local projections.

Remote object storage is not authoritative by itself. The signed commit graph is authoritative.

## Possible repository layout

```text
vault/
  objects/
    <hash-prefix>/<hash>          encrypted immutable chunks or packs
  commits/
    <commit-id>                   encrypted/signed commit envelope
  heads/
    main                          signed/encrypted pointer to latest accepted commit(s)
  keyring/
    epoch-<n>.json                encrypted key grants and membership events
  tombstones/
    ...                           revoke/delete markers where needed
```

The exact layout can be S3/R2-compatible object keys, not a filesystem.

## Commit envelope sketch

A commit should be small and structured enough to validate before applying:

```json
{
  "vault_id": "...",
  "commit_id": "hash-or-uuid",
  "parents": ["..."],
  "author_user_id": "...",
  "author_device_id": "...",
  "membership_epoch": 7,
  "created_at": "...",
  "base_head": "...",
  "object_manifest": [
    {
      "logical_path": "sources/raw/...",
      "object_hash": "...",
      "size": 12345,
      "content_type": "source-markdown"
    }
  ],
  "derived_policy": {
    "includes_compile_snapshot": true,
    "includes_search_index": false
  },
  "signature": "..."
}
```

The manifest itself may be encrypted if logical paths leak too much.

## Key hierarchy

### Device identity keys

Each device has a long-lived signing keypair:

- signs commits
- signs membership/key events generated by that device
- allows other devices to attribute changes

Each device also has an encryption public key for receiving vault keys.

### Vault epoch keys

Vault content is encrypted with a symmetric vault epoch key:

```text
vault_epoch_key[n]
```

Objects created during epoch `n` use that epoch's data-encryption keys, directly or via per-object keys wrapped by the epoch key.

### Key grants

A membership/keyring event grants an epoch key to a device:

```json
{
  "type": "grant",
  "vault_id": "...",
  "epoch": 7,
  "recipient_user_id": "...",
  "recipient_device_id": "...",
  "role": "editor",
  "wrapped_epoch_key": "encrypted-to-device-public-key",
  "granted_by_device_id": "...",
  "signature": "..."
}
```

### Role events

Roles should be represented as signed events rather than mutable rows only:

```json
{
  "type": "role_changed",
  "vault_id": "...",
  "user_id": "...",
  "role": "viewer",
  "membership_epoch": 7,
  "signed_by": "owner-device",
  "signature": "..."
}
```

The local DB can materialize the current membership table from the event log.

## Revocation semantics

Revocation cannot erase knowledge. If a device/user already decrypted content, they may have copied it.

Revocation can only mean:

1. revoked user cannot fetch/decrypt new canonical content after revocation;
2. revoked device cannot publish commits accepted by current members after revocation;
3. remote service stops serving current encrypted heads/keys to revoked accounts;
4. old encrypted packs can eventually be compacted into a new epoch and old packs garbage-collected.

### Revocation by epoch rotation

When removing a member/device:

1. Commit a signed revocation event.
2. Create epoch `n+1`.
3. Grant epoch `n+1` only to remaining devices.
4. New objects are encrypted under epoch `n+1`.
5. Optionally compact live content into new packs under epoch `n+1`.
6. Garbage-collect old epoch packs after retention window.

Until compaction and GC, old content encrypted under older keys may remain accessible to anyone who retained old keys and objects.

## Two-part server/client keys

A stronger revocation option is to split key material:

```text
content_key = KDF(client_secret_share, server_epoch_share)
```

The remote service only releases `server_epoch_share` to currently authorized users/devices.

Benefits:

- If a revoked device did not cache the server share, it cannot decrypt old remote objects again.
- Gives server-side access control some cryptographic bite.

Limits:

- If the device cached keys or plaintext, revocation still cannot erase knowledge.
- More complex offline behavior.
- Requires careful design so the server cannot decrypt alone.

A v1 may not need this if expectations are clear. It is worth considering for enterprise/team vaults.

## Sync protocol sketch

### Push

1. Local runtime creates canonical commit from local product state.
2. Encrypt objects/packs.
3. Upload encrypted objects.
4. Upload encrypted/signed commit.
5. Attempt remote head compare-and-swap from known base to new commit.
6. If head advanced by someone else, pull and merge/rebase.

### Pull

1. Fetch remote head.
2. Fetch missing commits and objects.
3. Verify signatures and membership epoch validity.
4. Decrypt objects with local epoch keys.
5. Apply canonical changes to local store.
6. Rebuild local projections like search/vector indexes if needed.

### Conflict handling

Some state can be append-only and naturally mergeable:

- new source added
- session event appended
- proposal created
- compile artifact added against a base commit

Some state needs conflict policy:

- vault config edited concurrently
- same source renamed/edited
- membership role changed concurrently
- two compile snapshots published from different bases

Early v1 should avoid clever automatic conflict resolution. Prefer explicit branches/conflicts for rare cases.

## What to sync vs rebuild

Sync:

- raw sources
- source metadata
- vault config
- user-visible accepted session/reply events
- accepted wiki/compile snapshots if canonical
- membership/key events
- signed commit metadata

Do not sync by default:

- search index rows
- vector index layout
- compile cache rows
- workflow engine journal internals
- transient model/tool transcripts
- local logs

Optional sync:

- compile cache, if encrypted and treated as optimization
- embeddings, if model/provider exposure and size are acceptable
- accepted compiled idea/topic graph, if part of canonical wiki state

## Sharing UX ideas

### Add collaborator

1. Owner invites collaborator.
2. Collaborator adds device.
3. Owner device grants current epoch key to collaborator device.
4. Collaborator pulls encrypted vault and rebuilds local projections.

### Remove collaborator

1. Owner signs revocation event.
2. Remaining devices rotate to new epoch.
3. UI explains: revoked user loses future remote access, but previously decrypted copies cannot be recalled.
4. Optional compaction/GC re-encrypts live state under new epoch.

### New device

1. User authenticates account.
2. Existing device approves new device or recovery key is used.
3. Existing device grants current epoch key.
4. New device syncs and rebuilds.

## Integrity checks

A device should reject commits when:

- signature is invalid;
- author device was not authorized at the commit's membership epoch;
- parent commit is unknown and not intentionally a fork;
- object hashes do not match;
- commit references objects unavailable after retry;
- membership/key event violates policy;
- canonical head update is not a valid descendant or accepted merge.

## Open questions

- Are logical paths encrypted or visible to the remote service?
- Is remote object size padding required?
- Is there a server-side account ACL in addition to cryptographic keying?
- Are public share links compatible with encrypted private vaults?
- Is every session/reply synced, or only user-promoted artifacts?
- Should compile outputs be canonical commits or local projections?
- Does v1 require two-part keys, or can it start with client-held epoch keys?
